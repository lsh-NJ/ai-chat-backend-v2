# Week 8：50 并发基线报告

## 结论

在本机单进程 API、固定 30 ms mock LLM、50 个并发用户的 40 秒测试中，两个 Chat 接口共完成 2,702 次请求，错误率为 0%。聚合 P50 为 150 ms，P95 为 370 ms，平均吞吐量为 67.98 请求/秒。

这说明当前版本通过了“50 并发、错误率低于 1%”的本周验收目标，但它不是生产容量上限：测试包含 0.3～0.7 秒用户等待时间，也没有逐步加压到系统饱和。

| 接口比例 | `/chat` 与 `/chat/stream` 权重各 1 |

## 最终结果

| 接口 | 请求数 | 失败数 | 错误率 | RPS | 平均 | P50 | P95 | 最大 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `POST /chat` | 1,333 | 0 | 0.00% | 33.54 | 172.96 ms | 150 ms | 370 ms | 1,067.67 ms |
| `POST /chat/stream` | 1,369 | 0 | 0.00% | 34.44 | 176.68 ms | 150 ms | 380 ms | 1,375.43 ms |
| 聚合 | 2,702 | 0 | 0.00% | 67.98 | 174.84 ms | 150 ms | 370 ms | 1,375.43 ms |

最终数据取自测试停止事件生成的 `results/week8_summary.json`，它会等待在途请求结束后再写入。Locust 默认 CSV 是周期快照，关停前可能少记录最后一小批已完成请求，因此不作为最终请求数来源。

## 业务结果核验

- 迁移生成的默认用户 1 个，Locust 用户 50 个。
- 数据库存在 2,702 个会话，与成功请求数一致。
- 数据库存在 5,404 条消息，恰好是每次请求一条 user 消息和一条 assistant 消息。
- `is_complete = false` 的消息为 0。
- retry stream 长度为 0，dead-letter stream 长度为 0。

因此，本次 0% 错误率不仅表示客户端收到了 200，也有对应的完整数据库结果。

## 如何解释这些数字

- P50 反映典型请求，本次普通与流式接口都是 150 ms。
- P95 比 P50 高约 220～230 ms，说明存在可见尾延迟；平均值 175 ms 无法单独表现这部分慢请求。
- 流式接口的平均值和 P95 只比普通接口略高。本 mock 的流式内容很短，因此不能据此推导真实长文本流的表现。
- 固定 mock 延迟只有 30 ms，其余时间包含认证查询、会话与消息事务、历史查询、HTTP 往返和运行时调度。各部分占比尚未被 tracing 直接测量，不能只凭本次结果断言具体瓶颈。
- 67.98 RPS 是当前封闭负载模型在指定等待时间下的结果，不是服务器最大吞吐量。

## 后续性能实验

如果后续专门学习性能架构，应按顺序增加证据：

1. 加入请求 tracing 和 SQL 计数，拆分认证、事务、历史查询和 LLM HTTP 时间。
2. 用阶梯负载逐步提高用户数，找到错误率或 P95 明显恶化的饱和点。
3. 在相同脚本下对比事务合并、连接池参数和多 Uvicorn worker，禁止同时修改多个变量。
4. 对真实流式模型单独测量首 token 时间和完整响应时间，不与本 mock 基线混用。
